# Ошибки и нарушения агентов

Назначение: хранить **уникальные классы** ошибок, выявленные по историческим чатам, для последующего улучшения базового промпта и workflow.

Повторный эпизод не создаёт новый класс, если причина и исправление те же. Он добавляется как подтверждение, новый симптом, новое условие возникновения или новое последствие.

Статусы:
- `BOOTSTRAP` — направление поиска, ещё не подтверждено историей;
- `OBSERVED` — найдено хотя бы в одном убедительном эпизоде;
- `CONSOLIDATED` — повторялось и уже позволяет сформулировать устойчивое правило.

## Подтверждённые классы

### E-001 — Перекладывание анализа результата на пользователя
Статус: `CONSOLIDATED`.

Симптом: агент даёт условные shell-конструкции или серию проверок так, что пользователю фактически приходится самому понять, что получилось и какой следующий шаг нужен.

Почему мешает: человек становится диспетчером ветвления, хотя его роль должна быть аппаратным оператором.

Правильный паттерн: если результат влияет на решение — запросить вывод, самому его разобрать и дать следующий шаг.

Evidence: `CHAT-001` — пользователь явно потребовал, чтобы агент сам проверял результаты команд и принимал решение. `CHAT-002` дополнительно формализует это в delivery protocol: агент сам определяет compile/link/scp-команды и не отдаёт пользователю техническое ветвление. `CHAT-008` — пользователь прямо потребовал, чтобы агент сам разбирал результаты ветвящихся команд, а не перекладывал вывод на оператора. `CHAT-010` — пользователь прямо закрепляет свою роль: он выполняет команды строго по указанию, а агент не должен требовать лишних действий/уточнений и должен сам вести техническое ветвление.

Кандидат в базовый промпт: усилить правило «вывод → анализ агента → следующая команда» и применять его не только к ошибкам, но и к поиску файлов/артефактов.

### E-002 — Неправильный баланс пошаговости
Статус: `CONSOLIDATED`.

Симптомы:
- в новых/ветвящихся операциях агент иногда шёл слишком широко;
- после замечания начал дробить даже уже знакомые рутинные действия;
- позднее дошёл до серии отдельных микрокоманд, создающих большой copy/paste overhead.

Почему мешает: крайности одинаково плохи — длинная цепь скрывает точку решения, а микрошаги превращают пользователя в оператора клавиатуры.

Правильный паттерн:
- **ветвящийся/неизвестный шаг**: небольшой блок → вывод → анализ агента;
- **рутинная доказанная последовательность без ветвления**: один копируемый блок на этап;
- отдельный микрошаг только если ошибка может быть опасной/разрушительной или результат действительно определяет продолжение.

Evidence: `CHAT-001` — сначала пользователь попросил строгую пошаговость, затем сам уточнил правило для рутинных действий, а позже отдельно потребовал прекратить дробление знакомого ISP bring-up на множество копирований. `CHAT-003` добавляет прямое замечание «опять не по порядку работаем» и эпизоды, где следующий test-stage был неясен оператору. `CHAT-004` окончательно формулирует баланс: risky/branching hardware шаги — по результатам, но обычный source→build→scp→run нужно давать цельным этапом без ожидания подтверждения очевидного build/copy. `CHAT-008` даёт наиболее чистую формулировку adaptive granularity: неизвестные/ветвящиеся шаги — по результату, знакомый bring-up — цельным блоком. `CHAT-009` — пользователь ещё жёстче фиксирует границу: пошаговые микрокоманды допустимы только для действительно опасных/ветвящихся мест; знакомый routine должен идти одним копируемым этапом. `CHAT-010` показывает обе границы правила: в начале пользователь требует строгую пошаговость для нового reverse, но после стабилизации lane отдельно просит не оборачивать camera-команды в SSH и не добавлять лишние действия. `CHAT-011` — после десятков микрошагов пользователь прямо запретил пошаговые команды кроме экстренных/ветвящихся случаев; это ещё одно сильное подтверждение adaptive granularity.

Кандидат: заменить простое «работай пошагово» на правило **adaptive step granularity**.

### E-003 — Неподтверждённые пути, имена и структура окружения
Статус: `CONSOLIDATED`.

Симптомы: агент несколько раз исходил из неверного расположения overlay, относительного пути к toolchain, ожидаемого имени helper-а или наличия уже подготовленного файла.

Почему мешает: получаются лишние сборки, ручные исправления и циклы «создай → проверь → выясни, что build вообще читает другое место».

Правильный паттерн: перед изменением пути/артефакта использовать уже полученные факты; если путь не подтверждён — сначала одной дешёвой командой определить реальный источник, затем менять его.

Evidence: `CHAT-001` — несколько итераций с OpenIPC overlay и относительными путями, а также поиск helper-а под неверным именем. `CHAT-006` — агент сначала предположил `MainApp`, затем `noodles` как источник userspace-логов; чтение фактического `start.sh` показало, что основной vendor process — `apollo`. `CHAT-008` — агент сначала искал старый helper под именем `h264_start`, хотя в checkpoint он лежал как `fh8626_h264_start`; фактический inventory быстро снял неопределённость. `CHAT-013` — агент снова перепутал назначение Windows-папок: архивы относились к Downloads, а visual captures/dumps — к Desktop/FH8626/captures; пользователь остановил выдуманный путь. `CHAT-014` — неверный IP `.203`, неверная версия owner (`v4.1.9` вместо уже подготовленного `v4.2.0`), неверное предположение о расположении `bringup_media_v3.sh` и забытый compiler path уже были явно записаны в handoff/workspace.

Кандидат: «не придумывать путь/имя/расположение; сначала использовать фактическое состояние».

### E-004 — Потеря shell/session environment
Статус: `OBSERVED`.

Симптом: Buildroot сначала починили очисткой `PATH`, но после перезапуска WSL Windows-пути снова вернулись и та же ошибка повторилась.

Почему мешает: рабочий рецепт был известен, но не стал частью воспроизводимого окружения.

Правильный паттерн: важные session-level параметры либо включать в каждый актуальный build-блок, либо переносить в устойчивый wrapper/env setup, а не надеяться на состояние старого терминала.

Evidence: `CHAT-001`.

### E-005 — Неверный способ SCP/SSH/TFTP передачи
Статус: `CONSOLIDATED`.

Симптомы:
- современный `scp` попытался использовать SFTP, которого на OpenIPC не было; требовался legacy режим;
- позднее агент забывал, что stock-система вообще не имеет SSH, и повторно предлагал SCP;
- в другом месте, наоборот, предлагался TFTP там, где на OpenIPC уже был более удобный SCP.

Почему мешает: транспорт выбирался не из текущего target-state, а по инерции.

Правильный паттерн: держать явную карту:
- OpenIPC development shell → подтверждённый SSH/SCP режим;
- stock shell → подтверждённый доступный transport;
- не переключать канал без причины;
- обязательные флаги считать частью команды, а не вспоминать после ошибки.

Evidence: `CHAT-001` — несколько независимых эпизодов. CHAT-007 усиливает класс: на OpenIPC агент несколько раз возвращается к TFTP вместо рабочего scp -O, а в stock затем предлагает SSH/SCP, хотя SSH там отсутствует. `CHAT-008` — legacy `scp -O` снова был забыт при передаче нового probe, хотя этот transport contract уже был известен.

Кандидат: зафиксировать transport contract для каждого активного окружения.

### E-006 — Потеря параметров сборки после смены WSL/shell
Статус: `OBSERVED`.

Это более узкий случай E-004: после новой сессии сборка снова запускалась без уже доказанного clean `PATH`.

Правильный паттерн: build-команда должна быть самодостаточной относительно параметров, которые регулярно теряются при новой сессии.

Evidence: `CHAT-001`.

### E-007 — Ненужное усложнение простых файловых/patch операций
Статус: `CONSOLIDATED`.

Симптом: для небольшого бинарного патча агент предложил Python, хотя задача нормально решалась обычными shell/binutils средствами; пользователь отдельно это остановил.

Почему мешает: увеличивает размер инструкции, поверхность ошибки и число зависимостей без инженерной выгоды.

Правильный паттерн: простой copy/patch/extract/byte replacement делать штатными shell-инструментами; Python использовать только когда он реально упрощает нетривиальную обработку.

Evidence: `CHAT-001`; `CHAT-004` — для анализа VPU dump агент снова предложил Python там, где пользователь предпочёл штатные `dd`/`ffmpeg`, после чего workflow был упрощён. CHAT-007: пользователь требует не заставлять его вручную править source, а позднее отдельно останавливает Python для простой бинарной правки. `CHAT-017` — для чтения нескольких little-endian GOT words агент предложил Python, хотя задача решалась штатными `dd` + `od`; пользователь отдельно остановил лишний Python.

### E-008 — Потеря текущего состояния системы
Статус: `CONSOLIDATED`.

Симптомы:
- агент забывал, находится камера в stock или OpenIPC;
- предлагал процессы/сервисы, которых в текущей системе быть не могло;
- предлагал ненужный reboot, хотя пользователь специально уже вернулся в нужное окружение;
- забывал доступность SSH в stock/OpenIPC.

Почему мешает: это один из самых дорогих классов ошибок в hardware bring-up — неправильный state assumption заставляет повторять boot/recovery и делает последующие выводы недостоверными.

Правильный паттерн: перед командами, зависящими от режима, держать явный **current-state header**: target environment, boot mode, transport, активные процессы/owners, dirty/clean state.

Evidence: `CHAT-001` — несколько признанных самим агентом потерь контекста. `CHAT-002` добавляет повторный пример: после reboot агент забыл, что `/tmp` очищается и test binaries/profile нужно снова загрузить из WSL. `CHAT-003` подтверждает тот же класс ещё раньше: агент повторно просил уже существующий dump, забывал очистку `/tmp` после RAM-boot reboot и нуждался в напоминании о dual-camera context. `CHAT-004` — агент предложил заново генерировать полный Apollo disassembly, хотя пользователь уже передавал его архивом; после напоминания artifact был найден и повторная работа отменена. CHAT-007: несколько дорогих потерь state — OpenIPC/stock перепутаны, предлагается лишний reboot, забывается локальная stock-копия и выбирается неправильный transport. `CHAT-008` — после потери `/tmp` прежние helper'ы пришлось заново разыскивать в checkpoint; эпизод показывает цену отсутствия явной active-artifact карты. `CHAT-011` — после power-cycle агент заново восстанавливал pipeline и пользователь справедливо напомнил, что он уже раньше запускался; выяснилось, что был пропущен обязательный cold-boot GPIO5 reset pulse. `CHAT-013` — текущий boot default, mount state и уже имеющиеся Apollo/JXF37 artifacts несколько раз приходилось напоминать; особенно чистый пример — повторный запрос Apollo, который уже был authoritative в workspace. `CHAT-014` — агент несколько раз терял active owner/version и текущую точку эксперимента, из-за чего предлагал старый `v4.1.9` и заново искал уже документированный toolchain. `CHAT-017` — агент несколько раз забывал известный TFTP/Windows root и существующий authoritative ARM_FULL, из-за чего предлагал неверный Downloads path и повторную подготовку Apollo. `CHAT-021` — после reboot использовался старый hardcoded heap range/PID и позже забывался уже известный `/bin/tftp`; состояние target/capability приходилось восстанавливать по предыдущему preflight.

Кандидат: добавить обязательную state-awareness для длинных hardware-сессий.

### E-009 — Лишние проверки после уже достаточного доказательства
Статус: `CONSOLIDATED`.

Симптомы:
- после успешного TFTP agent предложил ещё `md/crc32`, хотя пользователь счёл канал уже доказанным;
- reverse sensor vtable продолжался по полям, хотя для текущей цели достаточно было проверить загрузку библиотек и перейти к media stack.

Почему мешает: локально разумные проверки в сумме замедляют bring-up и уводят от реального блокера.

Правильный паттерн: перед проверкой задавать вопрос: **изменит ли её результат следующий технический шаг?** Если нет — пропускать, кроме финального acceptance/recovery gate.

Evidence: `CHAT-001`; `CHAT-005` даёт более ранний чистый пример: после успешного TFTP agent предложил ещё `md/crc32`, а пользователь прямо остановил это как «перепроверять до дыр» и потребовал переходить к сборке OpenIPC. CHAT-007: пользователь прямо спрашивает, нужен ли дальнейший разбор каждого sensor callback; агент признаёт, что reverse ушёл глубже текущего blocking question.

### E-010 — Слишком длинное планирование будущих веток
Статус: `OBSERVED`.

Симптом: агент тратит итерации на будущие fallback/альтернативные сценарии, хотя пользователь уже выбрал более простой рабочий режим и текущий blocker находится в другом месте.

Почему мешает: вместо закрытия текущего шага оператор получает дополнительную архитектуру и диагностику, которая пока не нужна.

Правильный паттерн: сначала реализовать выбранный пользователем основной путь; fallback/recovery расширять только когда он нужен для реального риска или отдельного запроса.

Evidence: `CHAT-003` — длительное проектирование U-Boot fallback оказалось лишним после того, как пользователь явно выбрал TFTP/OpenIPC как default и отдельную простую stock-команду. `CHAT-005` показывает раннюю форму того же класса: после того как gateway ping работал, agent ушёл в Windows ICMP/firewall диагностику, хотя пользователю нужен был только TFTP; пользователь остановил ветку словами «давай без icmp».

### E-011 — Необоснованная уверенность и обещание результата заранее
Статус: `CONSOLIDATED`.

Симптом: агент говорил в духе «после этого дам цельный probe / станет понятно», хотя текущие данные этого ещё не гарантировали; пользователь отдельно потребовал не предсказывать.

Почему мешает: создаёт ложное ощущение закрытого неизвестного и ухудшает доверие, особенно в reverse engineering.

Правильный паттерн: формулировать, **что конкретный шаг способен проверить**, а не обещать, что он обязательно закроет проблему.

Evidence: `CHAT-001`. `CHAT-008` — после ответа «осталось 2–3 узких неизвестных» до запуска последовал ещё длинный цикл ISP/VPU reverse и hardware tests; оценка близости была чрезмерно уверенной. `CHAT-009` — причина медленного SSH несколько раз объявлялась закрытой слишком рано: сначала random MAC/host-key generation, затем фактическая задержка была локализована дальше до CRNG readiness; источник показывает цену premature root-cause closure. `CHAT-013` — наличие JXF37/JXF37P drivers и 1080p formats было слишком быстро поднято до гипотезы о физическом wide sensor; stock boot/zoom trace позднее показал, что конкретная плата использует GC1054 1280×720 и upscale.

### E-012 — Диагностика, которая сама меняет/ломает исследуемое состояние
Статус: `CONSOLIDATED`.

Симптом: агрессивный preload/interposer запустил concurrent ioctl на тех же vendor fd и привёл к полному зависанию target; агент позже признал race/deadlock риск.

Почему мешает: диагностический инструмент перестаёт быть наблюдателем и становится новой причиной неисправности.

Правильный паттерн:
- сначала passive tracing/read-only observation;
- для stateful vendor drivers — один owner процесса/fd;
- не добавлять concurrent ioctl в живой pipeline без доказанной reentrancy;
- перед рискованным instrumentation иметь clean recovery/checkpoint.

Evidence: `CHAT-001`; `CHAT-003` — массовый live-MMIO rollback на работающем ISP привёл к зависанию камеры, после чего метод был запрещён и init перенесён в правильную pre-start lifecycle-фазу. `CHAT-009` — предложенный `rmmod isp/media_process` на живом vendor stack оставил висячий IRQ action; чтение `/proc/interrupts` после unload вызвало kernel Oops. Агент прямо признал, что unload делать было нельзя. `CHAT-011` — `LD_PRELOAD` stream tap на живом pipeline полностью повесил камеру; SSH и UART перестали отвечать. Это повторно подтверждает, что diagnostic instrumentation не должна добавлять concurrent/stateful ioctl на vendor fd. `CHAT-014` — попытка hot-replace через `kill -9` старого owner без reboot оставила vendor sensor/device state неконсистентным; новый owner получил массовые sensor-write failures и повторная init не прошла. `CHAT-021` — попытка сохранить большой physical-RAM dump в RAM-backed `/tmp` создала memory pressure/OOM и kernel убил Apollo; захват пришлось признать невалидным после этой точки.

### E-013 — Изменение артефакта без запроса на изменение
Статус: `CONSOLIDATED`.

Симптом: пользователь задал provenance-вопрос для передачи другому агенту, а агент самостоятельно продолжил редактировать master handoff.

Почему мешает: вопрос/анализ не равен разрешению мутировать authoritative artifact.

Правильный паттерн: различать режимы **read/analyze/report** и **modify**. Если пользователь сказал «файл больше не правим», любые дальнейшие ответы по теме должны быть только текстом до нового явного разрешения.

Evidence: `CHAT-001`. `CHAT-015` — пользователь снова прямо закрепил: не экспортировать новый handoff/архив, не повышать внешнюю версию и не показывать SHA-256 после каждой интеграции; сначала накапливать изменения и выдавать artifact только по запросу. `CHAT-020` — central integrator несколько раз выпускал/повышал master handoff (v16/v17/v18/v19), хотя пользователь уже задавал режим «интегрируй внутренне, экспортируй и повышай версию только по прямому запросу».

Кандидат: явное правило mutation scope для файлов, репозиториев и handoff-артефактов.

Evidence дополнен `CHAT-002`: пользователь отдельно закрепил, что архивы не нужно создавать/высылать при каждом локальном изменении — только при явном запросе или когда сформирован осмысленный hardware-test/handoff этап. В `CHAT-004` пользователь ещё точнее ограничил mutation scope: `FH8626_HANDOFF.md` обновить один раз по запросу и затем не трогать без новой необходимости/команды.

### E-014 — Игнорирование явно заданного протокола работы
Статус: `CONSOLIDATED`.

Симптом: пользователь подробно сформулировал обязательный file-delivery protocol (один versioned archive, готовые WSL/build/scp/test блоки, никаких больших исходников в сообщении), но следующий ответ агента снова отдал отдельные source-файлы вместо требуемого архива.

Почему мешает: пользователь вынужден повторно объяснять уже формализованный workflow, а агент возвращается к старому неудобному режиму буквально внутри того же чата.

Правильный паттерн: новый явно обозначенный operational protocol считать активным контрактом немедленно; перед следующим artifact delivery свериться с ним, а не действовать по предыдущей привычке.

Evidence: `CHAT-002`. `CHAT-014` — уже известные правила «пачки до decision boundary», `cd`, правильные lane/path/version и чтение handoff перед командами снова нарушались в одной сессии. `CHAT-015` — несмотря на ранее зафиксированный protocol, агент снова автоматически выпускал новые handoff versions и SHA после интеграции parallel findings, из-за чего пользователь повторно формализовал правило. `CHAT-020` — пользователь повторно формализует тот же запрет на unsolicited handoff/version/SHA, потому что central branch снова вернулся к старому export-поведению.

Кандидат: при появлении пользовательского process-contract обновлять рабочие правила/handoff до следующего действия и применять его сразу.

### E-015 — Неидемпотентные опасные команды без встроенной защиты
Статус: `CONSOLIDATED`.

Симптом: запуск нового media owner был дан как обычная shell-команда. Из-за повторного поступления/исполнения блока owner запустился второй раз на том же boot, хотя проект уже знал, что второй `/dev/isp` owner опасен.

Почему мешает: терминальная вставка может дублироваться, частично повторяться или быть исполнена пользователем дважды; критическая операция не должна полагаться только на внимательность оператора.

Правильный паттерн:
- опасные start/mutate операции делать идемпотентными;
- использовать process/lock guard;
- второй запуск должен физически отказываться стартовать;
- при сложной логике предпочтительнее подготовленный script/helper, а не длинный интерактивный multi-line `if`.

Evidence: `CHAT-002` — после повторного owner launch агент добавил атомарный lock и признал отсутствие guard своей ошибкой. `CHAT-003` подтверждает аппаратную цену этого класса раньше по хронологии: запуск второго media/ISP owner на одном boot приводил к hard hang. `CHAT-009` — повторные ISP owners и несколько открытых `/dev/isp` дали `isp, isp, isp` и dirty state; после этого направление сменено на единственный lifetime owner/daemon.

Кандидат: отдельное правило **critical commands must be self-guarding/idempotent**.

### E-016 — Избыточная техническая экспозиция вместо выполнения задачи
Статус: `CONSOLIDATED`.

Симптом: агент выдавал длинные рассуждения о call graph, вариантах движения и внутренних функциях, хотя пользователь просил быстрее писать код, коротко сообщать главное и приносить test-ready результат.

Почему мешает: полезный reverse превращается в чтение большого объёма промежуточного reasoning, а реальная разработка двигается медленнее.

Правильный паттерн: глубокий анализ выполнять внутри рабочего процесса; пользователю сообщать:
- что закончено;
- что изменилось;
- какой artifact/test готов;
- какой главный blocker остаётся.

Длинную техническую детализацию писать только в handoff/reverse notes или по запросу.

Evidence: `CHAT-002` — пользователь несколько раз требовал «коротко описывай», «детализация не нужна», «желательно сразу делай код». `CHAT-003` показывает предысторию той же проблемы: пользователь отмечал ощущение отсутствия прогресса из-за затянувшегося анализа и требовал перестать останавливаться на промежуточных шагах. `CHAT-004` повторяет тот же сигнал: пользователь несколько раз просил не останавливаться, не выдавать промежуточные файлы до готового шага и после затянувшихся A/B попросил перегруппироваться на восстановление API/lifecycle. `CHAT-013` — пользователь отдельно потребовал меньше промежуточных сообщений и автономный reverse до существенного milestone; серия «продолжай/что там/медленно работаешь» показывает, что частые partial updates не воспринимались как прогресс.

Кандидат: execution-first / concise-progress rule для reverse и портирования.

Evidence: CHAT-019 (partial export) добавляет небольшой operational пример: после неуспешной RTSP-auth проверки агент снова ушёл в дополнительный restart-path investigation; пользователь остановил лишние круги. Технически полезный HTTP snapshot path уже был известен и позже был выдан напрямую.

### E-017 — Недетерминированный операторский тест
Статус: `OBSERVED`.

Симптом: эксперимент требует от пользователя вручную отсчитывать секунды, менять физическое состояние сцены и потом выбирать одну из нескольких команд; границы состояний теряются в общем логе, а результат становится неоднозначным.

Почему мешает: evidence зависит от тайминга и интерпретации оператора вместо воспроизводимого test protocol.

Правильный паттерн:
- физическое действие задавать как один ясный этап: «сначала сделай X, затем выполни этот блок»;
- состояния `OPEN/CLOSED/REOPEN` сохранять раздельно или маркировать способом, который не может быть затёрт owner-log;
- не требовать ручного отсчёта, если можно разделить тест на последовательные команды;
- заранее сказать, какой именно вывод вернуть.

Evidence: `CHAT-003` — пользователь прямо сообщил, что не уверен в корректности timed test и позже не понял, какую команду считать «третьей стадией»; после этого схема была переделана на отдельные state files.

Кандидат: добавить правило deterministic hardware-test protocol.

### E-018 — Передача непроверенного build/artifact пользователю
Статус: `CONSOLIDATED`.

Симптомы:
- переданный owner archive не собирался с заявленным `-Werror` из-за оставшегося unused symbol;
- другой runtime ABI bug был заранее виден по compiler warnings: callbacks объявлены, но не использовались, однако archive всё равно ушёл на hardware loop.

Почему мешает: оператор тратит hardware/test итерацию на ошибки, которые агент мог обнаружить локальным compile/static check до передачи.

Правильный паттерн: перед выдачей test archive выполнить доступный lightweight preflight:
- compile с теми же flags, которые получит пользователь;
- host/self-test для чистой логики;
- проверить наличие всех archive members и соответствие compile command;
- warnings, которые противоречат ожидаемой архитектуре, анализировать, а не просто отключать `-Werror`.

Evidence: `CHAT-003`. `CHAT-009` — сгенерированный через `sed` source получил лишний `\&ch` и не компилировался; пользователь поймал ошибку на своей сборке, хотя такой syntax/preflight можно было проверить до hardware loop.

Кандидат: «не передавать пользователю test artifact, пока доступный локальный compile/preflight не прошёл».

### E-019 — Неверная поверхность исполнения команд
Статус: `CONSOLIDATED`.

Симптом: команда технически корректна, но оформлена не для того терминала/канала, которым пользователь реально управляет. В `CHAT-004` camera-side проверка была дана как SSH one-liner, после чего пользователь попросил все camera-команды давать непосредственно для serial UART shell, а WSL держать отдельным блоком.

Почему мешает: оператор вынужден мысленно распаковывать transport-wrapper, различать где WSL, где UART, где U-Boot и самостоятельно адаптировать команду.

Правильный паттерн:
- явно обозначать lane: `WSL`, `UART camera`, `U-Boot`;
- давать команду в форме, в которой она будет реально введена;
- не оборачивать target command в SSH без необходимости, если пользователь работает через UART.

Кандидат: добавить execution-surface contract для multi-terminal hardware work.

Evidence: `CHAT-008` — агент попросил прикрепить файлы из WSL как будто это обычная локальная поверхность; пользователь напомнил, что работает под Windows, после чего был дан путь через `/mnt/c/.../Downloads`. `CHAT-009` — WSL/UART/PlatformIO monitor продолжали смешиваться в длинных paste-блоках, из-за чего prompt/output попадали обратно как команды. `CHAT-010` — после успешного SSH PTY теста пользователь отдельно просит дальше давать camera-команды непосредственно для serial UART, без SSH wrapper. `CHAT-011` — при подготовке файлов агент снова действовал как будто пользователь работает в Linux desktop, и пользователь напомнил, что он под Windows/WSL; после этого путь был исправлен на `/mnt/c/...`. `CHAT-014` — WSL/Windows/camera lane снова путались при переносе captures: агент давал путь или действие не для той среды, где находился пользователь. `CHAT-016` — на stock агент снова дал `scp`/WSL-oriented transfer, хотя в handoff было зафиксировано: stock не имеет SSH, передача идёт через TFTP. Пользователь прямо потребовал перечитать handoff.

### E-020 — Нескоупленный поиск и мусорный вывод
Статус: `CONSOLIDATED`.

Симптом: широкий recursive `grep` прошёл по web-assets/бинарным данным и выдал большой бессмысленный поток. Пользователь отдельно указал на чрезмерный вывод; агент признал ошибку и добавил `--exclude-dir`, `--include`, конкретные каталоги и `head`.

Почему мешает:
- засоряет контекст;
- увеличивает ручной copy/paste;
- скрывает нужные совпадения среди binary/web noise;
- может заметно тормозить терминал.

Правильный паттерн: перед поиском ограничивать corpus по типу/директории и выводить только релевантный диапазон; полный artifact лучше передать агенту для локального поиска.

Кандидат: bounded-search rule для grep/find/objdump.

Evidence: `CHAT-016` — широкие/рекурсивные file scans заметно тормозили работу; пользователь потребовал focused workspace и точечный `grep/sed` по конкретным disassembly-файлам. `CHAT-017` — агент предлагал рекурсивный `find` по нескольким большим деревьям даже после того, как точный путь TFTP-файла уже был известен пользователю. `CHAT-021` — слишком широкий перенос Windows corpus через wildcard начал захватывать лишние деревья; пользователь потребовал копировать только корневые `fh_stock_*`/`fh_static_*` artifacts.

### E-021 — Перенос команд через обратный слеш вопреки базовому правилу
Статус: `OBSERVED`.

Симптом: в `CHAT-004` неоднократно выдавались shell/ffmpeg/find команды, физически разбитые через `\`, хотя исходный baseline прямо запрещает такой формат.

Почему мешает: serial/WSL paste уже показывает смешивание и частичное «съедание» строк; line continuation повышает вероятность повреждённой вставки и затрудняет повторное использование отдельных команд.

Правильный паттерн: каждая shell-команда должна физически помещаться на одной строке. Если команда слишком длинная — вынести параметры в переменные/файл или упростить этап, но не использовать `\`.

Это прямое нарушение baseline rule 9, независимо от того, был ли отдельный комментарий пользователя в момент каждого эпизода.

### E-022 — Запрос ручной работы, которую уже можно выполнить по имеющемуся артефакту
Статус: `CONSOLIDATED`.

Симптом: у агента уже есть полный firmware/SPI dump, но он всё равно просит пользователя на живой камере искать и вручную передавать `.ko`, `.so` и другие файлы. В `CHAT-006` пользователь прямо спросил, почему агент не может сам извлечь модули; после этого агент действительно извлёк `/app` из dump и продолжил анализ автономно.

Почему мешает:
- создаёт лишние target-команды и transfer-итерации;
- расходует внимание оператора на работу, не требующую физического доступа;
- увеличивает риск потери/несоответствия файлов;
- замедляет переход к содержательному reverse.

Правильный паттерн: перед просьбой что-либо найти/скопировать с target сначала проверить, нет ли нужного объекта уже в загруженном dump/archive/workspace/repository. Пользователь должен подключаться только там, где действительно требуется новое hardware evidence.

Кандидат: добавить обязательный **reuse available artifacts before asking the operator** rule.

Evidence: `CHAT-013` — агент снова попросил получить/дизассемблировать Apollo, хотя authoritative Apollo artifact уже был в workspace; пользователь прямо спросил, зачем он нужен ещё раз. `CHAT-016` — агент предложил заново запускать полный objdump/reverse pipeline, хотя пользователь уже передал готовые disassembly TXT; после замечания агент признал, что должен анализировать существующие тексты. `CHAT-017` — после получения live RW dump агент начал предлагать повторный objdump/установку ARM binutils и новый disassembly, хотя authoritative `apollo_unpacked_ARM_full.txt` уже был в specialist workspace; позже это было признано лишним.

### E-023 — Нет видимого прогресса на длинной reverse-задаче
Статус: `CONSOLIDATED`.

Симптом: пользователь несколько раз вынужден отдельно спрашивать, сколько ещё осталось, потому что серия reverse-шагов не показывает закрытые фазы, текущую границу и оставшиеся крупные блоки.

Правильный паттерн: держать короткий stage tracker — что доказано, какой blocker сейчас, какие 1–3 крупных блока остаются до следующего hardware milestone. Не давать временных обещаний; показывать прогресс по границам.

Evidence: `CHAT-007`. `CHAT-008` — пользователь повторно спрашивал, много ли осталось, затем «скок ещё осталось до запуска» и позже выражал нетерпение; карта remaining boundaries по ходу reverse явно отсутствовала. `CHAT-010` начинается с явного запроса зафиксировать текущий этап и дальнейший план; хороший stage summary быстро снял неопределённость без нового reverse. `CHAT-011` — пользователь несколько раз спрашивал, сколько осталось до запуска и когда закончится «вечный reverse»; отсутствие компактной boundary-карты продолжало ощущаться даже при реальном техническом прогрессе. `CHAT-013` — пользователь неоднократно спрашивал общий процент/остаток и просил сводку по модулям простым языком, несмотря на большой объём локальных reverse-находок. `CHAT-015` — пользователь просил не только проценты, но и объяснение, какие параллельные направления реально сдвинут functional parity; stage map по ценности subsystem оказался полезнее общего процента. `CHAT-020` показывает ограничение субъективных процентов: рядом появляются оценки reverse ~80–85%, 90–93% и 94–97%, что без фиксированного denominator хуже stage/module matrix.

### E-024 — Склейка shell-команд через `&&` / `;`
Статус: `CONSOLIDATED`.

Симптом: в `CHAT-007` неоднократно выдаются длинные цепочки вроде `scp && cd && nm/objdump`, хотя baseline требует один code block с одной командой на физическую строку.

Правильный паттерн: связанные команды держать в одном блоке, но каждую на отдельной строке; обычный этап не склеивать через shell operators.

Это прямое нарушение baseline rule 1.

Evidence: `CHAT-008` — до замечания о пошаговости агент выдавал условные цепочки `[ -n "$G" ] && scp ...`, снова смешивая проверку результата и действие в одной строке. `CHAT-009` — несмотря на уже сформулированный формат, встречались склеенные `chmod ... && run` и условные shell one-liners в операторском контуре. `CHAT-016` — длинная цепочка с `&&` и автоопределением objdump тихо оборвалась при отсутствии инструмента; внешне это выглядело как «команда зависла», а последующие действия не выполнились. `CHAT-017` — при переключении между «пошагово» и «пачками» агент несколько раз снова склеивал длинные WSL chains через `&&`; пользователь отдельно потребовал один block, но команды на отдельных строках.

### E-025 — CWD-dependent команда без явного `cd`
Статус: `OBSERVED`.

Симптом: относительный `output/host/bin/...` был дан с предположением, что терминал всё ещё в корне firmware; пользователь находился в `~/FH8626/libs`, и команда упала с `No such file or directory`.

Правильный паттерн: перед cwd-dependent блоком первой строкой `cd` в известный каталог либо использовать абсолютный путь.

Это прямое нарушение baseline rule 3.

Evidence: `CHAT-014` — перед `scp` снова был забыт обязательный `cd` в каталог checkpoint; пользователь исправил это напрямую.

### E-026 — Предположение наличия утилит на минимальном target
Статус: `CONSOLIDATED`.

Симптомы: на OpenIPC/stock предполагались `file`, `readelf`, `modinfo`, `which`, `tr`, `strings`; часть утилит отсутствовала и создавала лишние итерации.

Правильный паттерн: один раз снять capability map конкретного runtime (`busybox --list`, `command -v`), тяжёлый анализ делать в WSL, target использовать для runtime evidence.

Evidence: `CHAT-007`. `CHAT-013` — на минимальном target снова предполагались `file` и другие host-like utilities; команда упала, после чего анализ пришлось переносить в WSL. `CHAT-016` — stock shell не имел `od` и `tr`, BusyBox tar не поддерживал ожидаемый `-z`; несколько команд пришлось переделывать под фактический capability set. `CHAT-021` — агент снова предполагал gzip/hexdump/od/TFTP semantics без опоры на уже снятый tool preflight; BusyBox/stock capability различия вызвали лишние итерации.

### E-027 — Хрупкие interactive paste-блоки на UART
Статус: `CONSOLIDATED`.

Симптом: длинные многострочные shell-конструкции с `if/then`, кавычками, regex, command substitution и редиректами вводятся через serial monitor и частично смешиваются с echo/prompt/output. В результате:
- куски соседних команд слипаются;
- `grep -E` получает незакрытую кавычку и shell уходит в secondary prompt `>`;
- адрес `devmem` превращается в `0`/обрезанное значение;
- prompt/предыдущий вывод затем случайно вставляется обратно как команда.

Почему мешает:
- команда на экране уже не соответствует команде, которую агент анализирует;
- опасные MMIO/process действия могут быть выполнены с искажёнными аргументами;
- оператору приходится вручную спасать shell и восстанавливать, какая часть блока реально исполнилась.

Правильный паттерн:
- UART оставлять для коротких плоских команд и безопасных read-only checks;
- сложный control flow оформлять готовым script/helper-файлом, передавать через подтверждённый transport и запускать одной простой командой;
- для критичных адресов/процессов использовать guards и postcondition внутри самого helper;
- не строить serial workflow на длинных regex/quotes/multiline `if`.

Evidence: `CHAT-009` — многократные повреждённые paste-сессии, зависание в `>`, неверный `devmem 0`, сломанные process/grep команды. `CHAT-013` — длинные UART paste-блоки снова визуально смешивались с prompt/echo во время GPIO/sensor tests, подтверждая, что serial shell остаётся плохим каналом для сложной логики. `CHAT-014` — длинные serial paste-блоки продолжали искажаться визуально и смешиваться с prompt; это дополнительно подтверждает необходимость scripts/helpers для сложной camera-side логики. `CHAT-016` — stock UART shell снова был загрязнён кусками prompt/output и длинных вставок, из-за чего команды распадались и исполнялись вперемешку.

Кандидат: **complex shell logic belongs in transferred scripts, not interactive UART paste**.

### E-028 — Маскировка регрессии workaround-ом вместо сравнения с known-good baseline
Статус: `OBSERVED`.

Симптом: пользователь сообщает, что поведение **ухудшилось после недавних изменений** и раньше тот же путь был быстрым. Вместо того чтобы принять это как regression signal и сравнить before/after, агент объясняет новое поведение как нормальную характеристику системы и предлагает обходной механизм.

В `CHAT-010` каждый новый `ssh/scp` стал занимать 5–7 секунд после SSH-правок. Агент сначала объявил это нормальной стоимостью KEX на слабом ARM и предложил `ControlMaster`. Пользователь указал, что раньше обычный `scp -O` без multiplexing был быстрым. После этого агент признал трактовку неверной и вернулся к локализации паузы по boundaries.

Почему мешает:
- workaround может скрыть внесённую нами регрессию;
- known-good historical behavior отбрасывается в пользу удобного объяснения;
- причина остаётся в системе и позже проявляется в другом месте.

Правильный паттерн:
- фразу пользователя «раньше это работало/было быстрее, сломалось после наших правок» считать сильным regression evidence;
- сначала определить последний known-good state и минимальный diff;
- измерить boundary, где появилась деградация;
- workaround вводить только после того, как причина локализована или сознательно отложена.

Evidence: `CHAT-010` — ControlMaster-гипотеза была снята после прямого указания пользователя на pre-change fast SCP. `CHAT-011` — отдельная SSH-ветка подтверждает тот же regression pattern: пользователь фиксирует, что SCP раньше был почти мгновенным, а после наших SSH/network правок стал стабильно ждать около 5 секунд; решение пришлось возвращать к known-good network path и boundary timing.

Кандидат: **user-reported regression beats normalization/workaround; isolate the delta first**.

### E-029 — Временный bring-up hack теряет статус «временный» и рискует попасть в финальную архитектуру
Статус: `OBSERVED`.

Симптом: ради быстрого RAM bring-up правки вносятся прямо в общие OpenIPC overlay/init/network paths, generated rootfs или runtime image. Они могут быть технически полезны для эксперимента, но по мере роста чата перестаёт быть очевидно:
- что является чистым board-specific решением;
- что было временно отключено/заменено;
- что необходимо вернуть перед upstream/final port;
- какие изменения живут только в generated image и ещё не перенесены в canonical source.

В `CHAT-011` пользователь отдельно остановил этот риск и потребовал не забыть «всё вернуть обратно» при финальном оформлении порта. В reconciliation для handoff пришлось явно перечислить dev-only изменения: отключённый blocking NTP hook, временный uClibc compatibility runtime, development seed/network ordering, manual CPIO mutations и другие local-only fixes.

Почему мешает:
- рабочий dev image можно ошибочно принять за upstream-ready architecture;
- локальный workaround начинает менять общий OpenIPC behavior для других targets;
- proven state оказывается впереди source tree;
- следующий агент не знает, что нужно сохранить как факт, а что обязательно очистить.

Правильный паттерн:
- каждую временную правку маркировать `DEV_ONLY/TEMPORARY` сразу при внесении;
- вести cleanup/upstream-debt ledger рядом с текущим state;
- generated/rootfs mutation не считать canonical, пока она не перенесена в source/overlay;
- перед финализацией пройти отдельный reconciliation gate: revert, board-scope или clean upstream integration;
- handoff должен явно различать **current proven dev workaround** и **final intended architecture**.

Evidence: `CHAT-011` — пользователь потребовал сохранить напоминание о возврате временных правок, а обновление master handoff получило отдельный раздел «Do not confuse a proven development workaround with final upstream architecture».

Кандидат: обязательный **temporary-change / upstream-debt ledger** для bring-up проектов.

### E-030 — Firmware-supported hardware ошибочно принимается за установленное на конкретной плате
Статус: `OBSERVED`.

Симптом: наличие vendor driver, tuning blob, format ID и product-level `sensor_support` повышается почти до доказательства того, что соответствующий sensor физически установлен на исследуемой board revision.

В `CHAT-013` наличие `libjxf37_mipi.so`, `libjxf37p_mipi.so`, 1080p format и JXF37 tuning привело к приоритетной гипотезе «stock wide/Full-HD = JXF37». Затем hardware/stock evidence её опровергло:
- stock `sensor_probe` на этой плате выбирает `gc1054_mipi`;
- source VI остаётся 1280×720;
- 1920×1080 получается downstream через VPSS/VENC upscale;
- I²C JXF37 target не отвечает;
- реальный zoom/lens switch не меняет sensor driver или format.

Почему мешает:
- уводит reverse на другой BOM/board variant;
- sensor-specific AWB/geometry/tuning начинают трактоваться как неверные, хотя основной hardware path выбран правильно;
- software compatibility matrix подменяет board identity.

Правильный паттерн:
- vendor firmware support = **capability evidence**, не BOM evidence;
- hardware identity подтверждать stock runtime selection, physical bus response, board config + actual trace и/или visual/lens behavior;
- альтернативный driver оставлять `HYPOTHESIS/SUPPORTED_VARIANT` до target evidence;
- после опровержения явно помечать ветку superseded, но сохранять результат reverse как reusable knowledge для другой revision.

Evidence: `CHAT-013`.

### E-031 — Преждевременное объявление задачи полностью закрытой без requirement audit
Статус: `CONSOLIDATED`.

Симптом: агент сообщает, что задача «закрыта полностью» или «доведена до результата», потому что найден главный механизм, но не сверяет финальное состояние с исходным списком обязательных deliverables и evidence gates. После прямой просьбы пользователя провести полный аудит выясняется, что часть требований ещё не выполнена.

В `CHAT-014` reverse ветки AWB→CCM сначала был объявлен полностью закрытым по static evidence, хотя пользователь отдельно требовал runtime подтверждение. Только после его замечания появился точный внешний blocker, был подготовлен coherent owner path и получено hardware validation.

Почему мешает:
- «главная идея найдена» подменяет acceptance criteria;
- незакрытые runtime/selftest/field-level пункты теряются за уверенным summary;
- пользователь вынужден отдельно спрашивать «точно всё?» и запускать повторный аудит;
- handoff следующему агенту может получить завышенный статус.

Правильный паттерн:
- перед словом `DONE/COMPLETE` пройти исходный task checklist пункт за пунктом;
- разделить `SUBSTANTIAL_MILESTONE`, `STATIC_COMPLETE`, `HARDWARE_COMPLETE`, `TASK_ACCEPTED`;
- если для полного закрытия не хватает внешнего evidence — назвать конкретный blocker и запросить ровно его;
- итоговый status должен отражать самый слабый обязательный gate, а не самый сильный найденный результат.

Evidence: `CHAT-014`. `CHAT-015` усиливает риск слишком мелких specialist tasks: быстрый partial reverse был принят как завершённая работа, хотя пользователь ожидал долгую область с несколькими подзадачами и глубоким acceptance. `CHAT-016` — прямое подтверждение класса: Agent 1 сначала объявил Task 2 завершённым, а затем requirement audit оценил реальное закрытие лишь в 70–80% и перечислил недоделанные C8134/C883C, actuator arithmetic, D0630 history, numerical replay и selftests. `CHAT-017` — Agent 2 сначала объявил большой image-detail Task 2 завершённым, а после прямого checklist audit признал лишь ~55–65% выполнения; после дополнительного static/runtime evidence работа продолжалась до финального APC/NR3D/LTM closure.

Кандидат: обязательный **completion audit against original acceptance criteria** перед финальным закрытием задачи.

### E-032 — Предположение, что project-context автоматически даёт другим агентам доступ к физическим файлам
Статус: `CONSOLIDATED`.

Симптом: orchestration prompt ссылается на handoff/archive/disassembly как на «project files» и предполагает, что новый параллельный агент сможет их открыть автоматически. Агент получает смысловой контекст проекта, но его file sandbox не содержит нужных bytes.

В `CHAT-015` первый specialist правильно отказался делать exact reverse без `apollo_unpacked_ARM_full.txt`: контекст задачи был доступен, authoritative artifact — нет. После этого пришлось вручную прикреплять один и тот же handoff archive в каждый agent-chat.

Почему мешает:
- агент может начать «reverse по описанию» и повысить hypotheses до facts;
- пользователь становится ручным файловым router;
- universal prompt выглядит самодостаточным, хотя фактически зависит от невидимого attachment state;
- parallel launch ломается до начала содержательной работы.

Правильный паттерн:
- разделять **semantic project context** и **artifact availability**;
- перед стартом specialist lane иметь explicit required-artifact manifest;
- агент сначала подтверждает доступ к authoritative inputs, и только затем начинает exact reverse;
- отсутствующий artifact передаётся/подключается один раз через общий durable store, а не предполагается доступным;
- если bytes отсутствуют, не восстанавливать их по prompt-описанию.

Evidence: `CHAT-015`. `CHAT-016` начинается тем же file-access preflight: specialist видит project context, но exact reverse не начинает до отдельной загрузки handoff archive и authoritative Apollo dump. `CHAT-017` повторяет physical-attachment gap: Agent 2 не видел handoff в своём sandbox и правильно потребовал отдельную загрузку архива, несмотря на доступный project context.

Кандидат: обязательный **artifact-access preflight for every parallel agent**.

### E-033 — Слишком мелкая постановка parallel-agent задачи
Статус: `OBSERVED`.

Симптом: specialist получает узкий reverse одной-двух функций, быстро возвращает результат, после чего orchestration тратит сопоставимое время на запуск, передачу файлов, интеграцию и формулирование следующей задачи.

В `CHAT-015` пользователь прямо отметил, что первые два агента получили слишком простые задания и закончили слишком быстро. После этого модель была изменена на долгие последовательные `Task N` в тех же agent threads: не одна функция, а целый AE loop / detail pipeline с несколькими обязательными подзадачами и единым итоговым deliverable.

Почему мешает:
- высок overhead запуска и handoff на единицу reverse;
- specialist теряет уже набранный локальный контекст при создании нового чата;
- мелкая задача стимулирует преждевременное `DONE` вместо field-level subsystem closure.

Правильный паттерн:
- делить работу по достаточно крупной **cohesive subsystem boundary**;
- один specialist thread может выполнять `Task 1 → Task 2 → Task 3`;
- каждая задача имеет depth/acceptance checklist, а не целевое время;
- scope должен быть независим от других lanes, но достаточно велик, чтобы amortize context/setup cost.

Evidence: `CHAT-015`.

### E-034 — Отсутствие liveness-сигнала во время реально долгой локальной операции
Статус: `OBSERVED`.

Симптом: пользователь дал агенту автономный режим и попросил не засорять чат промежуточными findings. При длинном локальном reverse/tool-call несколько минут нет никакого ответа, и это воспринимается как зависание или остановка работы.

В `CHAT-016` пользователь несколько раз спрашивает «ты тут?», «опять завис?» и затем формулирует более точное правило: промежуточные **технические выводы** можно не сообщать, но при долгой операции нужно кратко показывать, что именно сейчас выполняется и что процесс жив.

Почему мешает:
- оператор не различает «агент глубоко работает» и «tool call завис/ответ потерян»;
- возникает лишний ping-pong «продолжай / ты тут?»;
- слишком частые подробные updates мешают автономности, а полная тишина ломает доверие.

Правильный паттерн:
- содержательные findings — milestone/blocker-based;
- liveness update — короткий, без chain-of-thought: текущий блок, что проверяется, есть ли blocker;
- давать heartbeat только если операция заметно затянулась;
- после tool failure/обрыва немедленно сообщить, где именно продолжится работа.

Evidence: `CHAT-016`.

Кандидат: **silent reasoning + sparse liveness heartbeat** для длительных autonomous tasks.

### E-035 — Потеря specialist-role / загрязнение scope между параллельными агентами
Статус: `OBSERVED`.

Симптом: агент получает явно выделенную параллельную область, но после загрузки общего handoff начинает отчитываться по scope другого specialist lane.

В `CHAT-017` Agent 2 был назначен на `CDD6C / D0B2C / GOT table identity`. После появления handoff он внезапно вернул результат по `C9740 → C949C → C9898` — ветке Agent 1. То есть общий handoff/context временно вытеснил локальную role assignment.

Почему мешает:
- parallel work начинает дублироваться вместо ускорения;
- ownership boundaries становятся недостоверными;
- основной интегратор может принять чужой result как новый independent evidence;
- расходуется specialist context window на уже закрытую область.

Правильный паттерн:
- у каждого specialist lane должен быть короткий immutable `ROLE_SCOPE.md` / task header;
- после загрузки/смены большого handoff агент повторно сверяет **свою** область, exclusions и expected deliverable;
- перед финальным summary проверяется, что все основные функции результата принадлежат текущему scope;
- общий project handoff не должен иметь приоритет над последней явной specialist assignment;
- при обнаружении cross-scope полезного факта — записать interface note и вернуться в свой lane, а не захватывать чужую задачу.

Evidence: `CHAT-017`.

Кандидат: обязательный **specialist role-lock / scope preflight** для multi-agent orchestration.

### E-036 — Нестабильные проценты готовности без фиксированной модели покрытия
Статус: `OBSERVED`.

Симптом: агент отвечает на вопрос «на сколько процентов готово» одной субъективной цифрой, но denominator не зафиксирован. В одной центральной сессии оценки reverse/current-day меняются между примерно `80–85%`, `90–93%` и `94–97%` в зависимости от того, что именно мысленно включено в scope.

Почему мешает:
- одинаковая фраза «reverse готов на X%» может означать function identification, field-level exactness, runtime integration или hardware parity;
- цифры выглядят противоречиво даже при реальном прогрессе;
- оператору труднее понять, что осталось физически сделать.

Правильный паттерн:
- проценты вторичны, primary representation — module/status matrix;
- минимум разделять `REVERSE_COVERAGE`, `SOURCE_IMPLEMENTATION`, `HARDWARE_PARITY`, `VISUAL_PARITY`;
- denominator задавать списком subsystem/gates и не менять между соседними отчётами;
- крупный progress-report должен перечислять closed/open boundaries, а процент только суммировать их.

Evidence: `CHAT-020`.

Кандидат: **fixed progress ontology + module matrix вместо плавающей общей оценки**.

### E-037 — Diagnostic capture без resource budget на constrained target
Статус: `OBSERVED`.

Симптом: read-only операция считается «безопасной» только потому, что она ничего не пишет в hardware state, но не учитывается объём RAM/tmpfs/I/O.

В `CHAT-021` попытка сохранить примерно полный physical-RAM image stock FH8626 в `/tmp` создала memory pressure/OOM; kernel убил Apollo. Даже частичного многомегабайтного dump оказалось достаточно, чтобы испортить runtime state.

Почему мешает:
- read-only capture всё равно может разрушить наблюдаемую систему;
- после OOM любые последующие данные того boot нельзя считать clean evidence;
- повтор эксперимента требует reboot и восстановления state.

Правильный паттерн:
- перед capture считать size и available target memory/storage;
- для constrained target использовать small targeted ranges;
- крупные данные stream/chunk-transfer на host с немедленным удалением;
- иметь per-capture resource budget и abort threshold;
- после OOM/process death явно маркировать dataset invalid after event.

Evidence: `CHAT-021`.

### E-038 — Capture manifest описывает intended state вместо фактически наблюдаемого
Статус: `OBSERVED`.

Симптом: experiment archive называется и размечается по ожидаемому действию, но фактический physical/application state отличается.

В `CHAT-021`:
- white-light coupled capture был записан как TELE, хотя пользователь наблюдал WIDE;
- archive, названный `MIC_UPLINK`, по UART/dataflow оказался talkback/downlink через AO/speaker path.

Почему мешает:
- неверный label превращается в ложное evidence;
- downstream diff/reverse может приписать изменения неправильной подсистеме;
- переименование без provenance стирает историю ошибки.

Правильный паттерн:
- manifest должен хранить intended state **и observed/validated state** отдельно;
- после capture сверять UART/process/sensor evidence с label;
- исправление хранить как metadata correction, не молча переписывать raw source;
- superseded/mislabeled capture сохранять в provenance, но исключать из canonical state set.

Evidence: `CHAT-021`.
